# Per-company Microsoft 365 single sign-on — design

Date: 2026-10-30
Status: Approved design, awaiting spec review

## Goal

Let a company's users sign in to MyPortal with their Office 365 (Entra ID)
account, with as little friction as possible, while admins keep control over
which Microsoft identity belongs to which MyPortal account.

Success means: a linked user clicks *Sign in with Microsoft* (or types their
work email) and lands in MyPortal without entering a MyPortal password or,
when Microsoft already performed MFA, a MyPortal TOTP code.

## Decisions

| Topic | Decision |
|---|---|
| Linking | Auto-link on first Microsoft sign-in when the verified email matches exactly one eligible MyPortal user; admins can link, re-link and unlink manually. |
| Password login | Per-company `sso_mode`: `off` (default), `optional`, `required`. Super admins are always exempt from `required`. |
| MyPortal TOTP | Skipped when the ID token's `amr` claim contains `mfa`; otherwise the existing TOTP rules apply. |
| Login page | A *Sign in with Microsoft* button plus email-domain detection. |
| App registration | One shared multi-tenant public PKCE client (the existing `get_effective_pkce_client_id`) against the `/organizations` authority, scopes `openid profile email`. |

## Existing building blocks

- `app/api/routes/auth.py::_complete_login_response` — creates the session,
  records the login and writes the `auth.login.succeed` audit row.
- `app/services/m365_oauth_transactions.py` — single-use, encrypted,
  10-minute OAuth transactions (Redis or database).
- `app/services/m365.py::generate_pkce_pair`, `get_effective_pkce_client_id`
  and `validate_microsoft_id_token` (JWKS signature, `aud`, `exp`, `iat`,
  `iss` bound to `tid`).
- `/m365/callback` in `app/main.py` — the only redirect URI registered on the
  PKCE client. Its current state helpers bind transactions to a logged-in
  session, which a sign-in does not have.
- `companies.csp_tenant_id` and `company_m365_credentials.tenant_id` — together
  the company's *effective tenant* (CSP tenant when mapped, otherwise the
  credential tenant), as used by `m365_repo.list_company_ids_for_app_tenant`.
- `company_email_domains` — unique email domain → company mapping.
- Passkey login's pre-login binding cookie pattern
  (`_set_passkey_login_cookie` / `_validated_passkey_login_cookie`).

## Data model

One migration (created with `/new-migration`, idempotent):

```sql
CREATE TABLE IF NOT EXISTS user_sso_identities (
  id INT AUTO_INCREMENT PRIMARY KEY,
  user_id INT NOT NULL,
  provider VARCHAR(32) NOT NULL,          -- 'm365'
  tenant_id VARCHAR(64) NOT NULL,         -- Entra tid, lower-case
  object_id VARCHAR(64) NOT NULL,         -- Entra oid, lower-case
  upn VARCHAR(255) NULL,
  email VARCHAR(255) NULL,
  linked_via VARCHAR(16) NOT NULL,        -- 'auto' | 'admin'
  linked_by_user_id INT NULL,
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  last_login_at DATETIME NULL,
  UNIQUE KEY uq_user_sso_identity (provider, tenant_id, object_id),
  UNIQUE KEY uq_user_sso_provider (user_id, provider),
  FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE,
  FOREIGN KEY (linked_by_user_id) REFERENCES users(id) ON DELETE SET NULL
);

ALTER TABLE companies
  ADD COLUMN IF NOT EXISTS sso_mode VARCHAR(16) NOT NULL DEFAULT 'off';
```

The SQLite fallback gets the equivalent DDL through the existing migration
runner conventions. All timestamps are UTC.

The link is keyed on the immutable `(tid, oid)` pair. UPN and email are kept
for display only and are refreshed on each successful sign-in.

## Units

| Unit | Responsibility |
|---|---|
| `app/repositories/user_sso_identities.py` | Get by `(provider, tenant, oid)`, get by user, create, delete, touch `last_login_at`/UPN/email, list for a company. Parameterised SQL only. |
| `app/services/sso_policy.py` | `get_company_sso_mode`, `companies_for_tenant(tid)` (effective tenant match, `sso_mode != 'off'`), `password_login_allowed(user)`, `discover(email)`, and `can_manage_link(actor, target_user)`. |
| `app/services/sso_login.py` | Build the authorize redirect; resolve a callback into a login outcome (user + MFA satisfied, or a failure reason). Token redemption and ID-token validation are injected so tests can stub them. |
| Routes in `app/api/routes/auth.py` | `GET /auth/microsoft/start`, `POST /auth/microsoft/discover`, `POST /auth/microsoft/totp`. |
| `/m365/callback` hand-off in `app/main.py` | Recognise the SSO state envelope before the "must be logged in" check and delegate to `sso_login`. |
| Companies feature handlers | Edit company → *Microsoft sign-in* section: mode, linked users, link/unlink, tenant directory search. |
| Templates / JS | `auth/login.html` button and detection; `admin/company_edit.html` section and modal; `app/static/js/company_sso_admin.js`; `app/static/js/login_sso.js`. |

## Sign-in flow

1. **Start** — `GET /auth/microsoft/start?email=<optional>`
   - Generate a PKCE pair, a nonce and a random browser binding.
   - Create an `m365_oauth_transactions` record with
     `flow="sso_login"`, `code_verifier`, `nonce`, `client_id`,
     `redirect_uri`, `binding_hash` (SHA-256 of the binding) and `login_hint`.
   - Set the binding in an HttpOnly, `SameSite=Lax`, `Secure` (when the
     request is secure) cookie scoped to `/`, max-age 600 s. `Lax` is
     required because Microsoft returns via a top-level GET.
   - Redirect (303) to
     `https://login.microsoftonline.com/organizations/oauth2/v2.0/authorize`
     with `client_id`, `response_type=code`, `response_mode=query`,
     `redirect_uri=_build_m365_redirect_uri()`, `scope=openid profile email`,
     `state`, `nonce`, `code_challenge` (S256), `prompt=select_account` and
     `login_hint` when an email was supplied.
   - The signed `state` envelope is `{"sso_transaction_id": "<id>"}`, distinct
     from the session-bound `{"transaction_id": …}` envelope.
   - Rate-limited per client IP using `auth_repo.register_login_attempt`.

2. **Callback** — `/m365/callback`
   - If the signed state carries `sso_transaction_id`, consume the
     transaction and handle it with `sso_login`; the session-bound path is
     untouched for every other flow.
   - Reject (generic failure) when the transaction is missing, expired,
     replayed, not `flow="sso_login"`, or the binding cookie is absent or does
     not hash to `binding_hash`. Clear the binding cookie in every outcome.
   - If Microsoft returned `error`, redirect to `/login` with a plain message;
     log the AADSTS detail.
   - Redeem the code at the `/organizations` token endpoint with the PKCE
     verifier.
   - Validate the ID token with `validate_microsoft_id_token(client_id=…)`
     and require `nonce` to equal the transaction's nonce and `oid` to be
     present.

3. **Resolve the user** (`sso_login.resolve`)
   - `companies = sso_policy.companies_for_tenant(tid)`. If empty → failure
     `tenant_not_enabled`.
   - **Linked**: an identity exists for `(m365, tid, oid)`. The user must be
     active and belong to one of `companies` (primary `company_id` or a
     `user_companies` membership). Otherwise → `company_mismatch` /
     `account_disabled`.
   - **Auto-link**: no identity exists. Take the verified address
     (`email` claim, falling back to `preferred_username`), lower-cased. It
     must match exactly one active user who belongs to one of `companies`
     and has no `m365` identity yet. Create the identity with
     `linked_via='auto'` and audit `auth.sso.link`. Zero or several matches
     → `no_link`.
   - Every failure shows the same message on `/login`: *"No MyPortal account
     is linked to this Microsoft account. Contact your administrator."*
     (`tenant_not_enabled` may say SSO is not enabled for the organisation,
     since that reveals nothing about MyPortal accounts.)

4. **MFA decision**
   - `amr` contains `mfa` → complete the login with TOTP enrolment skipped.
   - Otherwise, if the user has TOTP authenticators → store a pending-login
     record (single-use transaction, 5 minutes, bound to a new binding
     cookie) and render the existing TOTP prompt, which posts to
     `POST /auth/microsoft/totp`. A valid code (via `_verify_and_claim_totp`)
     completes the login; wrong codes count toward the account lockout.
   - Otherwise → complete the login and keep the existing forced-enrolment
     redirect to `/security/2fa`.

5. **Complete** — `_complete_login_response(auth_method="m365_sso", …)`
   gains a `skip_totp_enrollment: bool = False` parameter. On success the
   browser is redirected to the post-login destination, the identity's
   `last_login_at`, UPN and email are updated, and the audit row records
   `authentication_method="m365_sso"` and `mfa_satisfied_by="microsoft"` or
   `"myportal_totp"`.

## Enforcement of `required` mode

`sso_policy.password_login_allowed(user)` returns `False` when the user is
not a super admin, has an `m365` identity, and any company they belong to has
`sso_mode='required'`.

- `POST /auth/login` — after the password and lockout checks pass, a refused
  user gets 403 *"Your organisation requires Microsoft sign-in."* with
  `{"sso_required": true}` so the page can offer the Microsoft button. The
  check runs only after a correct password so it is not an account
  enumeration oracle.
- Passkey authentication verify — same refusal.
- Password reset — no reset email is sent for refused users; the response
  stays the generic one.
- Unlinked users of a `required` company keep password login, so turning on
  `required` never locks out someone who has not been linked.

## Email detection

`POST /auth/microsoft/discover` with `{"email": "…"}` returns
`{"sso": "off" | "optional" | "required"}`. The result comes only from the
email's domain via `company_email_domains` → `companies.sso_mode`, and is
`off` unless that company also has an effective tenant. It never looks up
users, so it reveals nothing about accounts. It is rate-limited per IP and
CSRF-exempt like `/auth/login`.

Login page behaviour (`app/static/js/login_sso.js`, progressive
enhancement):

- Always render *Sign in with Microsoft* as a plain link to
  `/auth/microsoft/start`.
- On email blur/submit, call discover. `optional` → show *Continue with
  Microsoft* above the password field. `required` → navigate to
  `/auth/microsoft/start?email=…`.
- Without JavaScript the button and the password form still work.

## Admin experience

### Edit company → *Microsoft sign-in* section

New `ce-section` (`id="ce-microsoft-sign-in"`) in the *People & access*
nav group of the existing workspace, listed for anyone who passes
`can_manage_link` for the company (unlike the super-admin-only items beside
it).

- Overview chips: *Tenant connected* / *Not connected*, current mode,
  *N users linked*.
- Mode: segmented control *Off / Optional / Required* with one-line help.
  *Required* is disabled until the company has an effective tenant and at
  least one linked user. Choosing it lists the users who are not linked
  (they keep password sign-in).
- Linked users: searchable list of the company's MyPortal users with status
  pills (*Linked · auto*, *Linked · admin*, *Not linked*), Microsoft UPN and
  last Microsoft sign-in (`<span data-utc>`), and an empty state explaining
  the feature.
- *Link* opens a `div.modal[role=dialog]` that searches the tenant directory
  through the existing Graph app connection
  (`/users?$search="displayName:…" OR "userPrincipalName:…"`, `$select=id,
  displayName,userPrincipalName,mail`) and stores the chosen user's `oid`.
  Linking an `oid` already linked elsewhere is refused with a message naming
  the current MyPortal account. Linking replaces the target user's existing
  identity (re-link).
- *Unlink* asks for confirmation.
- All forms post with CSRF and work without JavaScript.

### Other surfaces

- Admin user page: read-only *Microsoft sign-in* row (UPN or *Not linked*)
  with *Unlink* under the same permission rules.
- User profile: shows the linked Microsoft account; the user may unlink it
  only when none of their companies is in `required` mode.

### Who can manage

`sso_policy.can_manage_link(actor, target_user, company_id)`:

- Super admins: any user.
- Company admins (existing company management scope): the company's mode,
  and links for users of that company — but not super admins, and not users
  who also belong to a company outside the actor's management scope.

### API

REST endpoints with Swagger docs, under the existing companies router:

- `GET /api/companies/{id}/sso` — mode, tenant status, linked identities.
- `PUT /api/companies/{id}/sso` — set mode.
- `GET /api/companies/{id}/sso/directory?q=` — tenant directory search.
- `PUT /api/users/{id}/sso-identity` — link (`{"object_id": …, "company_id": …}`).
- `DELETE /api/users/{id}/sso-identity` — unlink.

## Audit and logging

Through `audit_service.record`:

- `auth.sso.link` / `auth.sso.unlink` — `linked_via`, actor, tenant, hashed
  oid.
- `auth.login.succeed` — `authentication_method="m365_sso"`,
  `mfa_satisfied_by`.
- `auth.sso.fail` — identified users only (avoids an unbounded audit write
  primitive), with the reason: `no_link`, `company_mismatch`,
  `account_disabled`, `tenant_not_enabled`, `password_login_refused`.
- `company.sso_mode.update` — old and new mode.

Unidentified failures go to the structured log only, with the email hashed
as `_hash_email` does today.

## Error handling

- Microsoft errors, expired/replayed state, binding mismatch, token or nonce
  failures → `flash_redirect("/login", <plain message>, "error")`; AADSTS
  detail is logged, not shown.
- Graph directory search failures in the admin modal → inline error in the
  modal; the section still renders.
- No change to how existing `/m365/callback` flows behave.

## Testing

pytest-asyncio with the existing fixtures; Microsoft token exchange and
ID-token validation stubbed.

- Callback: linked happy path; auto-link with one match; no auto-link with
  zero or two matches or when the user already has an identity; tenant with
  no SSO-enabled company; company mismatch; inactive user.
- State: replayed or expired transaction; missing or wrong binding cookie;
  nonce mismatch; non-SSO envelopes still use the session-bound path.
- MFA: `amr` with `mfa` skips TOTP and enrolment; without it, TOTP required
  when enrolled (correct, wrong, lockout) and enrolment forced when not.
- `required` mode: password, passkey and reset refused for linked users;
  super admins exempt; unlinked users unaffected; generic responses
  unchanged.
- Discover: response shape; no user lookup; rate limit.
- Admin permissions: company admin within scope; refused for super admins
  and cross-company users; `required` refused without tenant or links;
  duplicate `oid` refused.
- Migration idempotency; audit of every SQL statement in touched files for
  parameterisation.

## Rollout

- Every company starts at `sso_mode='off'`; nothing changes until an admin
  opts in.
- No new environment variables; the shared PKCE client and `/m365/callback`
  redirect URI already exist.
- Change log entry via `/changelog-entry`.
- Wiki page *Microsoft 365 single sign-on* under `docs/wiki` for admins:
  enabling, linking, `required` mode, and the super admin exemption.

## Out of scope

- Just-in-time creation of MyPortal users.
- Other identity providers (Google, generic OIDC, SAML).
- IdP-initiated sign-in from Microsoft My Apps.
- Per-company app registrations for sign-in.
- Microsoft single logout; MyPortal logout ends only the MyPortal session.
